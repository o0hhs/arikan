Когда оператор оставляет только белый список — мессенджеры, госуслуги, банки, — обычные протоколы замолкают. CDN даёт адрес, который в этот список попадает: клиент идёт на **домен раздачи**, сеть CDN принимает запрос и отдельным соединением идёт к **источнику** на вашей ноде.

```text
Клиент ──TLS──> cdn.example.com   (домен раздачи, DNS ведёт на CDN)
CDN    ──TLS──> origin.example.com (домен источника, DNS ведёт на ноду)
                     └── mihomo на ноде
```

:::note
Это тот же обход, что и раньше через каскад с белым IP, но вместо дорогого адреса, который завтра могут вычеркнуть из списка, здесь инфраструктура CDN. У неё много точек входа, и ограничить её целиком труднее.
:::

## Что понадобится

1. Нода с публичным IPv4 (в панели — **Ноды**).
2. Два имени: **домен источника** (ведёт на ноду) и **домен раздачи** (ведёт на CDN).
3. Сертификат на домен источника — панель выпустит его сама, если домен указан в карточке ноды.
4. Домен раздачи с сертификатом на стороне CDN — обычно провайдер выпускает его сам.
5. CDN с режимом «источник» (pull-origin). Список подходящих — ниже.

:::caution
**Домена без CDN не хватит, и CDN без домена не хватит.** Два имени — это два разных участка соединения: клиент видит только домен раздачи, а CDN соединяется с нодой по домену источника. Один и тот же домен для обоих не годится.
:::

## Шаг 1. Домен источника и сертификат ноды

Домен источника — это обычное имя, указывающее на IP ноды. В панели он нужен ещё и потому, что по нему выпускается сертификат: CDN ходит к источнику по HTTPS и проверяет сертификат.

1. Заведите A-запись, например `origin.example.com` → IP ноды.
2. В панели откройте карточку ноды и укажите этот домен в поле **Домен**.
3. Дождитесь, пока панель выпустит сертификат (**Ноды** → карточка ноды, состояние сертификата).

Если сертификата нет, CDN при проверке источника вернёт ошибку, а в его логе будет отказ TLS.

:::note
У ноды без домена сертификат выпускается на IP-адрес. Такой сертификат CDN, как правило, не принимает: большинство провайдеров не даёт выключить проверку сертификата источника. Поэтому домен источника — не формальность.
:::

## Шаг 2. Подключение под CDN

В панели два пресета под CDN — выбор зависит от того, пропускает ли провайдер POST.

- **VLESS · TLS · XHTTP · CDN**: режим `stream-one` — восходящий поток одним POST, нисходящий потоковым GET. Для CDN, у которых жив POST; крупные провайдеры его всё чаще режут — Яндекс закрыл POST прямо на бэкенде.
- **VLESS · TLS · XHTTP · CDN · GET-аплоад**: режим `packet-up`, восходящий поток — GET-запросами, у которых данные едут заголовками (`X-Data`), а тело пустое. Это проходит там, где POST не живёт. Клиентам нужен свежий Xray (26.3.27+ в Happ, v2RayTun) или mihomo (1.19.32+); приложения на sing-box этот протокол не получат.
- Порт можно оставить предложенный или сменить: наружу смотрит CDN, а не этот порт.
- Сертификат — тот самый домен источника из шага 1.

Дальше в блоке **За прокси** этого подключения укажите адрес, по которому к вам пойдут клиенты, — то есть **домен раздачи**:

- **Адрес для клиентов**: `cdn.example.com`
- **Порт для клиентов**: `443`
- **SNI для клиентов**: `cdn.example.com`

Подписка после этого отдаёт клиентам адрес CDN, а не ноды.

## Шаг 3. CDN-ресурс

Порядок настройки у провайдеров различается, но смысл один:

1. Создайте ресурс с **источником** `origin.example.com` (тип — статика или общий HTTP).
2. Привяжите **домен раздачи** `cdn.example.com` к ресурсу: провайдер выдаст CNAME, который нужно прописать в DNS.
3. Выпустите сертификат на домен раздачи — обычно это делает сам провайдер.
4. Убедитесь, что провайдер **не переписывает методы и тело запроса** и пропускает POST.

:::tip[Какой провайдер выбрать]
Из российских CDN с режимом «источник» обычно берут **Yandex Cloud CDN**, **VK Cloud**, **Selectel**, **Timeweb**, **Beget** и **Beeline**. Их общее достоинство в том, что они сами с большой вероятностью остаются доступны там, где включают белые списки.

**Cloudflare для этой схемы не подходит**: Роскомнадзор его блокирует, и у него нет обычного pull-origin для произвольного транспорта. Cloudflare Workers — тем более не CDN: это исполняемый код на краю сети, он не работает прозрачным прокси.
:::

## Шаг 4. Что отвечает на «обычные» запросы

CDN рано или поздно обратится к источнику по пути, которого нет в вашем транспорте, — и этот ответ увидит сканер или сам CDN. Чтобы нода не выглядела пустым сервером, у неё есть **своя страница** (см. [Ноды](/arikan/nodes/nodes/#страница-ноды)): файлы в `/opt/mikan/data/node/www` на сервере ноды, собственный сертификат, порт 443 или `127.0.0.1:18443`, если 443 занят подключением.

Положите туда свой `index.html` и `404.html` — нода их не перезапишет. Порт 80 нода тоже держит: отвечает на проверки ACME и на всё остальное отдаёт **301** на HTTPS, так что `http://origin.example.com` ведёт на обычный сайт.

## Проверка по слоям

Не меняйте настройки XHTTP, пока не убедились, что работает каждый слой до него. Порядок из статьи:

1. Домены и сертификаты сходятся: `origin.example.com` ведёт на ноду, `cdn.example.com` — на CDN, у обоих валидный сертификат.
2. Источник отвечает по HTTPS **напрямую**, минуя CDN:

   ```bash
   curl -sv https://origin.example.com/ -o /dev/null
   ```

3. CDN получает ответ от источника — видно в логе или консоли CDN.
4. Запрос к транспортному пути доходит до ноды.
5. Клиент получил свежую подписку: в ней адрес `cdn.example.com`.

Только после этого имеет смысл трогать режим, паддинг и остальные поля XHTTP.

Проверить слои одной командой можно скриптом из репозитория:

```bash
bash scripts/cdn-check.sh --cdn cdn.example.com --origin origin.example.com --path /ваш-путь/
```

Он ничего не меняет: смотрит DNS обоих имён, сертификат источника (срок, имена, издателя), ответ источника напрямую, ответ CDN и время ответа на обоих концах, а затем шлёт POST и GET на транспортный путь. Провал называет слой, и по нему уже видно, что чинить. Отдельно он ловит `405` на POST: это ответ на вопрос, пропускает ли выбранный CDN POST-аплоад, — для GET-аплоада не приговор, с ним смотрите строку выше.

## Если не работает

| Что видно | Где искать |
|---|---|
| `502` | разрешение домена источника, порт, TLS/SNI, сертификат, заголовок `Host`; тот же запрос напрямую, без CDN |
| `504` | время ответа источника напрямую и через CDN; у некоторых CDN окно ожидания фиксировано (Yandex требует ответ за 5 секунд), и увеличить его в nginx не выйдет |
| `403` | правила доступа и WAF на стороне CDN |
| `404` | заголовок `Host` и путь: запрос попал не в тот обработчик |
| `405` | метод: CDN пропускает только `GET`, `HEAD`, `OPTIONS`. Для пресета с POST (`stream-one`) — смена CDN; для GET-аплоада не приговор: его аплоад идёт GET, смотрите следующую строку |
| `413` | ограничение размера тела запроса: проверьте на каждом слое |
| `429` | лимиты частоты и числа соединений |
| Работает, потом замирает | максимальная длительность соединения и простой у CDN, таймауты чтения; `proxy_read_timeout` задаёт паузу между операциями чтения, а не длительность всего ответа |
| Работает по Wi-Fi, не работает в мобильной сети | это подтверждает, что маршрут есть, но не то, что узел CDN доступен у конкретного оператора: проверьте другой узел или другого провайдера |

## Если перед нодой уже стоит nginx

Тогда CDN приходит на nginx, а тот раздаёт запросы по путям: транспортный путь — на локальный порт XHTTP, всё остальное — на страницу ноды. Шаблон для `http`-блока:

```nginx
server {
    listen 443 ssl;
    server_name origin.example.com;

    ssl_certificate     /etc/letsencrypt/live/origin.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/origin.example.com/privkey.pem;

    # Транспортный путь: подставьте свой (панель показывает его в подключении).
    location /ваш-путь/ {
        proxy_pass http://127.0.0.1:11443;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_buffering off;
        proxy_request_buffering off;
        proxy_read_timeout 3600s;
        proxy_send_timeout 3600s;
    }

    # Всё остальное — обычный сайт.
    location / {
        root /var/www/origin;
        try_files $uri $uri/ =404;
    }
}
```

:::caution
`proxy_buffering off` и `proxy_request_buffering off` здесь обязательны: с буферизацией nginx накапливает тело запроса и ответа, и потоковый транспорт не работает. Порт `11443` — из подключения **VLESS · TLS · XHTTP · CDN**, подставьте свой.
:::

## Чего панель не делает

- **Не настраивает CDN за вас**: ресурс, домен раздачи и сертификат заводятся в консоли провайдера.
- **Не выдаёт сертификат на домен раздачи**: это сторона CDN.
- **Не обходит белые списки гарантированно**: у разных операторов и регионов доступность узлов CDN различается, и результат зависит от сети.

Схема требует внимания: после изменений у CDN или в ядре цепочку нужно проверять заново. Для сервиса к этому добавляются расчёт нагрузки, лимиты соединений, мониторинг источника и план замены CDN.
