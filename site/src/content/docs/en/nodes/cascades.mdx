---
title: Cascades
description: Exit to the internet through another panel node over the panel's own tunnel, chains of three or more servers.
---

A cascade sends a protocol's traffic through another node of the panel:

```text
client → node A → node B → internet
```

Clients connect to node A, and sites see node B's address. This way you can keep the entry point where it is not blocked and exit in the country you need.

## How the traffic gets there

The panel carries the traffic itself, so no connection is opened from the entry's country into the exit's:

```text
client → node A → the panel's tunnel → node B → internet
```

- Node B keeps a connection of its own to the panel (port 443, the panel's own certificate). The panel takes it as the exit's stream.
- The panel opens a second connection to node A — its usual API connection, upgraded — and node A's clients ride it as streams, one per client connection.
- The panel pairs each stream with the exit's connection and copies the bytes.
- Inside the entry node the core points at a SOCKS5 proxy on the node's own loopback (`127.0.0.1:47105`). The exit dials the site, resolves its name with its own resolver and leaves by its own rules: the exit sees the same traffic an inbound of its own would.

Node A never dials node B's address. An exit that is not in the tunnel carries nothing, and the protocols behind it simply do not work.

:::caution
Update the nodes before the panel turns the tunnel on: a node older than the tunnel refuses the state that names a loopback exit and keeps its previous one (with the old direct dial). Its card says its state is refused until it is updated.
:::

## Set up

1. Open the connection on node A and in the **Way out to the internet** field choose "Via a node".
2. In the **Exit node** field choose node B.
3. Save.

The **Cascade** button on a node card shows the tunnel: whether the panel holds node A's bridge, whether node B keeps its stream, and which exits are in the tunnel and which are reserves.

Requirements:

- node B is a remote node with its own join key (the panel's own node cannot be an exit);
- the panel answers on a public address with a certificate the node trusts (Let's Encrypt, not its self-signed one) — the exit's connection goes to it;
- both nodes run a version with the tunnel.

## Reserves

Every exit gets up to three reserves among the panel's other exits (the nodes some enabled inbound or relay leaves through). When the exit's tunnel is down, the entry tries the reserves for every new connection, one after another. Connections already open end with the tunnel: the next ones take the reserve.

The card shows them: the reserves are marked, and each exit says whether it is in the tunnel now.

## What does not cross the tunnel

The tunnel carries TCP connections. UDP flows (QUIC and HTTP/3 sites, WireGuard-type protocols) do not cross it: an inbound that exits through another node serves TCP only.

## Longer chains

There is also the **Where other nodes' traffic goes next** field on the exit node: direct, through this node's WARP, or through one more node. This is how chains of three or more servers are built: node A sends to node B over the tunnel, and node B sends the same traffic on to node C over another. The panel will not save loops, and a protocol cannot choose its own node as the exit.

## A cascade through WARP

WARP becomes the last link of the chain: sites see Cloudflare's address, not the exit node's. You can send everything that goes through the exit into it, or only some protocols — the rest then leaves through the same exit directly, as two independent paths.

```text
client → node A (RF) → the panel's tunnel → node B (abroad) → internet
                                                          ↘ WARP → internet
```

1. Set WARP up on node B: the **WARP** button on its card, either registration or your own config, see [WARP](/arikan/en/nodes/warp/). Make sure the check passes.
2. On node A open the protocol's settings: **Way out to the internet → Via a node**, **Exit node → B**, then **How the traffic leaves → WARP**. The choice shows only when B has a WARP that is on; protocols without it leave through B directly.
3. When it is the relay rather than a protocol that leaves through B (longer chains), the same choice is made for all of it: in node B's **Cascade** window, **Where other nodes' traffic goes next → WARP** sends every unmarked stream from other nodes there.

The panel will not save a route through WARP while node B has no WARP that is on: without it the traffic would leave directly from the exit node's own address. The cascade window shows WARP's state beside the route, and when WARP is not set up or is off, the button leads to that node's WARP page. While such a route is set, WARP cannot be turned off or deleted: the panel refuses.

On node A's card every exit shows the real chain, and the same exit stands twice when both paths go through it: `B → WARP` and `B → internet`. Beside it are the address sites see, WARP or WARP+, and when it was last checked.

**If WARP goes down**, its route does not leave directly: connections simply fail until WARP is back. This is the same rule as for a protocol that exits through WARP — the exit node's address does not leak. The direct route through the same node keeps working. The card says so: WARP is marked "down" and the reason is named (see [WARP](/arikan/en/nodes/warp/#check)).

:::caution
Both ends know a route through WARP: the entry marks its connections, the exit sends the marked ones to WARP. A node older than this version does not know the mark, so the panel does not build such a route for it — the connections fail rather than leave directly. Update both nodes.
:::

## Checking a cascade

Open **Check node** on the entry node (A), see [Nodes](/arikan/en/nodes/nodes/#check-node). The panel checks through the cascade from node A's side and shows the address sites see:

- **no way out**: the tunnel is not up (see the Cascade button: which end is down), or the exit has no internet.

On the exit node itself, if others go out through it, the Cascade button shows its stream to the panel.

## The relay port

Older panels and nodes carried a cascade over a hidden relay on the exit: a VLESS REALITY listener on a TCP port of its own. The panel still opens it for nodes that are not updated yet, and it is the port on the Cascade page. Once every node runs the tunnel, nothing uses it.
