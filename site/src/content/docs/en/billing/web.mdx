Where Telegram does not open, a VPN cannot be bought in the bot: buying a VPN would already require a VPN. The shop on the subscription address takes the payment in an ordinary browser. Telegram is not involved.

A purchase follows the same path as the bot. The payment appears under **Payments**, the `subscription.paid` webhook goes out once the subscription is granted, and a repeated notice from the payment system does not grant it twice. The browser coming back to the site does not grant anything by itself — the panel reads the invoice back from the provider and checks the amount and the currency.

## Turn it on

<Steps>

1. **Settings → Subscription → Buy in the browser.** The switch stays off until you turn it on. Selling is switched on separately: without it the shop has nothing to charge.

2. Mail for the sign-in code: an SMTP server, a port, a From address and the encryption. The password is not shown back. Without mail a new buyer cannot sign in. A subscription that already exists can still be renewed with its link.

3. The address after payment is where the payment system sends the browser. Empty: the shop page. It is not an address the buyer's browser supplies.

4. If your own site calls the shop's API, list its origin (for example `https://example.com`), one per line. The shop's own address needs no entry.

</Steps>

The shop's address is the subscription address plus `shop`. The subscription page gains a **Renew in the browser** button: it binds that subscription to the session and opens the shop.

## How people buy

A new buyer enters an email and the code from the letter (or opens the link in the letter). The session is an `HttpOnly` cookie, which a script on the page cannot read. They then pick a plan, a term and a device pack, and pay.

## What they pay with

The same card holds three providers. The bot lists the same three.

- **Platega.** The merchant id and the secret from the platega.io cabinet, and a payment method from their documentation (SBP by default). The callback address the panel shows is pasted into the Platega cabinet. The callback carries the same merchant id and secret; the panel still reads the invoice back and applies it only when the status is CONFIRMED, the currency is RUB and the amount covers the invoice.
- **RollyPay.** An API key and the cash register's signing secret. The terminal id is optional when you pay with a key. The callback address is pasted into the cash register as `callback_url`. The signature is HMAC-SHA256 of `timestamp.body` with the cash register's secret. The invoice is paid only after a status call answers `paid`, with the same amount and currency check.
- **CryptoBot.** This is the marketplace add-on `cryptobot` that already exists; the panel does not implement it again. Install the add-on and enter the Crypto Pay API token from @CryptoBot.

Secrets never reach the browser: an empty field on save keeps the previous one. Platega and RollyPay publish no refund in the API this panel uses, so a promo code is not taken on them — a late discounted payment could not be returned. CryptoBot takes a promo code when the add-on says it can refund.

A renewal does not need an email. The subscription link is enough. It is the same secret the subscription page already trusts.

Telegram sign-in is an extra, when a bot is connected. The widget needs the shop's domain set in BotFather (`/setdomain`). The bot token never reaches the browser: the panel checks the signature itself. Stars are not in the shop — they are paid inside Telegram. The balance is offered only to someone signed in with Telegram, because it is that Telegram account's balance.

The referral programme and partner credits count for a purchase that has a Telegram account. A purchase by email or by a subscription link does not: there is no Telegram account to attach them to.

## An API for your own site

The same methods the shop page uses, under `…/shop/api/`:

| Method | Path | What it does |
| --- | --- | --- |
| GET | `/shop/api/config` | Whether email sign-in is set up, and the bot name for the widget |
| POST | `/shop/api/code` | The letter with the code |
| POST | `/shop/api/login` | Sign in with the code; sets the session |
| POST | `/shop/api/telegram` | Sign in with the Telegram widget |
| POST | `/shop/api/token` | Renew with a subscription link |
| GET | `/shop/api/offers` | Plans, terms, device packs, payment methods |
| POST | `/shop/api/promo` | Check a promo code, without spending it |
| POST | `/shop/api/pay` | An invoice. The answer carries the payment address |
| GET | `/shop/api/order?order=` | The invoice's status. It does not grant anything |

Requests that change something send the header `X-Mikan-Shop: 1`. A form on another site cannot set it, and the origin has to be on the list: otherwise there is no CORS header and the request is refused. For such a site, signing in returns a session token (`Authorization: Bearer`), because the browser will not attach the cookie to a request from another site. No panel secret is in the answer.
