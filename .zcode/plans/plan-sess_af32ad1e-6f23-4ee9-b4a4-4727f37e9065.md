## Ситуация

Сервер собран из коммита `4abda809` — это **ветка `feature/olcrtc`**, не вошедшая в main (проверено по SLSA-аттестации образа `ghcr.io/o0hhs/mikan:0.6.0.0`). Отсюда всё остальное:

- нумерация миграций старая, до мержа: `0016_referrals.sql` + `0017_node_olcrtc.sql` (в релизе 0016–0031 заняты апстримом, а наши стали 0032–0035);
- ключ подписи в бинаре — старый (`Z3wSIPBS…`, сейчас это `release.CatalogKey`);
- в образе нет апстримовских фич 0.5.1.0 (аддоны, бот-аддон, проверки нод).

Поэтому ни панель, ни `mikan update` без аргументов обновление не предложат: версия 0.6.0.0 выше 0.5.1.1, а подпись нашего релиза их старым ключом не проверяется. Путь один — **ручное обновление на точный дайджест** плюс правка нумерации миграций в базе, чтобы goose применил апстримовые 0016–0031 и наши 0033–0035 (данные реферальной программы при этом сохраняются).

## Шаг 0. Диагностика (на сервере, ничего не меняет)

```bash
cd /opt/mikan
grep -E '^MIKAN_(IMAGE|VERSION|UPDATE_CHANNEL)' .env
docker compose exec -T panel mikan version && docker compose exec -T panel mikan status
docker compose exec -T -e PGPASSWORD="$(sed -n 's/^MIKAN_POSTGRES_PASSWORD=//p' .env)" \
  postgres psql -h /run/postgresql -U mikan -d mikan \
  -c "select version_id, is_applied from goose_db_version order by 1"
```
Ожидаемо: `MIKAN_IMAGE=ghcr.io/o0hhs/mikan:0.6.0.0`, применены версии 1–17. Если набор другой (например уже 0032+ с другого стенда) — скажи, план скорректируем.

## Шаг 1. Скрипт-починка базы (готовлю я, запускаешь ты)

Я напишу `scripts/migrate-pre-merge-db.sh` и **отрепетирую его локально** на настоящих образах: подниму Postgres, прогоню на нём `ghcr.io/o0hhs/mikan:0.6.0.0` (она уже есть локально), затем скрипт, затем `0.5.1.1` — и проверю, что панель стартует и данные на месте.

Что делает скрипт:

1. проверяет окружение (compose, `.env`, текущий максимальный version_id — ждёт 16/17);
2. делает резервную копию: `.env.before-pre-merge`, `mikan database backup` внутрь `/opt/mikan/data/panel/`;
3. останавливает панель (`docker compose stop panel`);
4. скачивает с `raw.githubusercontent.com/.../v0.5.1.1` апстримовые `0016…0031` и сверяет **sha256 каждого файла** с таблицей, зашитой в скрипт;
5. применяет их по порядку через `psql -1 -v ON_ERROR_STOP=1` (тела `-- +goose Up`, маркеры для psql — просто комментарии) — без этого goose потом откажется работать из-за «дыры» в нумерации;
6. приводит в порядок учёт goose: `update goose_db_version set version_id = 32 where version_id = 16` (файл тот же самый, sha256 `a24bf669…` — я сверил оба побайтово), `delete … where version_id = 17` (olcrtc-миграция, её таблицы остаются мусором), `insert` строк для 16–31;
7. проверяет результат: `max(version_id) = 32`, число строк в `referral_*` до и после совпадает, новые таблицы/колонки апстрима на месте (spot-check `addon_sources`, колонки `users`/`bound_devices`);
8. печатает баннер: бэкапы, следующий шаг, как откатиться (`install-fork.sh --rollback <дамп>` или `mikan database restore`).

Запуск: `sudo bash scripts/migrate-pre-merge-db.sh` (скрипт положу в репозиторий, чтобы ты брал его с `raw.githubusercontent.com`, как install-fork.sh; локальный путь — для отладки).

## Шаг 2. Образ на релиз (именно по дайджесту)

```bash
sudo mikan update ghcr.io/o0hhs/mikan@sha256:5163b0070613d0c6ba011fa45d6c7cfcea66168a567b6aa1b84af6a6c22f2c6c
```
Позиционный TARGET в `mikan update` не сверяет версии — это тот путь, который открыт для «переезда вниз»; установщик сам делает бэкап, останавливает панель, прогоняет `database migrate` (применит 33–35; 32 уже помечена), поднимает стек, при неудаче откатывается по своей таблице решений. Простой — минуты.

## Шаг 3. Хостовый `mikan` из релиза (новый ключ)

Старый установщик на хосте не сможет читать наши подписанные релизы (в нём старый ключ), поэтому автоматические обновления будут молчать:

```bash
curl -fL -o /tmp/mikan-x86_64 https://github.com/o0hhs/mikanaddons/releases/download/v0.5.1.1/mikan-x86_64
echo "0ca7c9adaa1692845923fb26ae115ada586cb87d65b2821f0720016c50ba0b12  /tmp/mikan-x86_64" | sha256sum -c -
sudo cp -a /usr/local/bin/mikan /usr/local/bin/mikan.before-0511
sudo install -m 0755 /tmp/mikan-x86_64 /usr/local/bin/mikan
```
(для arm64-сервера — `mikan-aarch64`, хэш `f337f159…`).

## Шаг 4. Проверки

```bash
cd /opt/mikan && sudo mikan status && sudo mikan update --check
```
- `mikan status`: образ `…@sha256:5163b007…`, версия 0.5.1.1;
- `update --check`: «0.5.1.1 is the latest release» (следующий релиз предложится сам);
- в панели: обзор открывается, «Протоколы»/«Пользователи» живы, реферальные коды и балансы на месте, в «Аддонах» подтягивается маркетплейс и ставится официальный бот (в 0.5.1.1 исправлен ключ каталога — без этой правки маркетплейс на форке не работал бы);
- если на сервере есть удалённые ноды — при включённом «ноды следуют за панелью» они обновятся сами (у нод базы нет, миграции их не касаются).

## Опционально: убрать мусор от olcrtc

Таблицы olcrtc и её ключи в `settings` релизу не мешают (никто их не читает). Удалить их можно после успешного обновления — список таблиц я достану из `0017_node_olcrtc.sql` (`4abda809`) и дам готовый `DROP`.

## Что делаю я (в репозитории)

1. `scripts/migrate-pre-merge-db.sh` — починка базы с бэкапом, проверкой sha256 апстрим-миграций и откатом при ошибке.
2. Локальная репетиция всей цепочки (0.6.0.0 → скрипт → 0.5.1.1) на Docker с настоящими образами и проверка, что панель поднимается и данные целы.
3. README не трогаю — их ведёт параллельный агент; инструкцию по переезду с до-мержевых сборок при желании добавлю отдельно, когда он закончит.

## Риски и договорённости

- Три уровня бэкапа: скрипт, `mikan update` (сам), плюс апстрим-миграции применяются на копию до остановки панели — откат возможен на любом шаге (`mikan database restore` из дампа или `install-fork.sh --rollback`).
- Данные реферальной программы сохраняются (мы не удаляем таблицы, а переносим их номер 16→32; файл миграции идентичен — сверил).
- olcrtc-фича с сервера исчезнет (ветка остаётся в репозитории; в релизе вместо неё VK TURN на vk-turn-proxy).
- Если на сервере `MIKAN_UPDATE_CHANNEL=beta` — после переезда вернуть на `stable`, иначе в один момент может приехать бета.
